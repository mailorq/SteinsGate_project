# projectctl — подготовка и запуск steinsgate_mailor

CLI на стандартной библиотеке Python: готовит `.env`, проверяет машину и
поднимает стек через Docker Compose. Работает одинаково на Windows и Linux.

```
scripts/projectctl.py init | validate | up | down | status | logs | inspect | adopt
```

## Требования

- Docker Engine + Compose v2 (`docker compose version`)
- Python 3.10+, сторонних пакетов не нужно

## Быстрый старт

### Ubuntu

```bash
python3 scripts/projectctl.py init          # создаст .env, если его нет
nano .env                                   # EMAIL_HOST_USER, EMAIL_HOST_PASSWORD
python3 scripts/projectctl.py validate
python3 scripts/projectctl.py up
```

### Windows PowerShell

```powershell
python scripts\projectctl.py init
notepad .env
python scripts\projectctl.py validate
python scripts\projectctl.py up
```

Для реального сервера вместо первой команды:

```bash
python3 scripts/projectctl.py init --mode production --host steins.example.com
```

Остановить (данные сохраняются):

```bash
python3 scripts/projectctl.py down
```

## Команды

| Команда | Что делает | Код возврата |
|---|---|---|
| `init` | Создаёт `.env`, если его нет; в существующий файл добавляет только отсутствующий `EMAIL_DELIVERY_QUOTA_SECRET` для безопасного обновления | 1 при ошибке аргументов |
| `validate` | Docker, файлы Compose, `.env`, секреты, порт, публикация сервисов, владение ресурсами | 1 при любой проблеме |
| `up` | Запускает стек **только после успешной** `validate` и ждёт HTTP 200 от `/api/anime` | 1 при сбое запуска или health-check |
| `down` | Останавливает контейнеры и сети проекта. **Тома не удаляет** | 1 при сбое |
| `status` | `compose ps` + health-check | 1 если Compose упал или сервис не отвечает |
| `logs` | Логи сервисов проекта | 1 при сбое Compose |
| `inspect` | Показывает контейнеры, сети и тома проекта. Ничего не удаляет | 0 |
| `adopt` | Признаёт существующие тома и сети принадлежащими этому каталогу | 1 без подтверждения |

### Флаги

`init`:

| Флаг | Назначение |
|---|---|
| `--mode demo\|production` | Режим, по умолчанию `demo` |
| `--host` | Домен, обязателен для `production` |
| `--port` | Порт публикации фронтенда, по умолчанию 4173 |
| `--rotate-secret` | Заменить `SECRET_KEY` в существующем `.env` |
| `--allow-debug` | Записать `DEBUG=True`, недопустимо в `production` |
| `--no-tls` | `production` без TLS-терминатора (`HTTPS_ENABLED=False`) |

`validate` и `up` принимают `--allow-debug`; `up` — ещё `--no-build` и
`--timeout` (секунды ожидания health-check). `logs` — `--tail N`, `--follow` и
имя сервиса. `adopt` — `--yes` для неинтерактивного запуска.

## Режимы

**`demo`** — фронтенд публикуется **только на `127.0.0.1`** через overlay
`compose.demo.yaml`. Подходит для локальной работы и отладки.

**`production`** — фронтенд слушает все интерфейсы, `ALLOWED_HOSTS` берётся из
`--host`, `HTTPS_ENABLED=True`. `DEBUG=True` в этом режиме запрещён: отладочный
режим не должен работать на публичном интерфейсе.

Режим записывается в `.env` как `PROJECTCTL_MODE`. Неизвестное значение —
ошибка, а не молчаливый откат к `production`.

> `HTTPS_ENABLED=True` только включает редирект, Secure-cookie и HSTS. Сам
> TLS-терминатор (nginx/Caddy/Traefik с сертификатом) в проект не входит и
> скриптом не проверяется. Без него вход сломается: браузер не отправит
> Secure-cookie по http.

## Изоляция

Стек всегда поднимается под именем проекта **`steinsgate_mailor`**, зашитым в
код и не переопределяемым через окружение. Все операции скоупятся этим именем,
поэтому другие Docker-проекты на машине не затрагиваются.

> Если раньше вы поднимали стек командой `docker compose up` из корня, он
> работал под именем каталога (`steinsgate_project`) и имел **свою** базу.
> `projectctl` использует другое имя проекта, поэтому стартует с чистой БД.
> Старые данные не удаляются и остаются в томах прежнего проекта.

## Что скрипт делает и чего не делает

Меняет состояние Docker ровно двумя командами:

- `compose up -d [--build]` — образы, контейнеры, сети и тома при первом запуске;
- `compose down` — контейнеры и сети. **Тома остаются.**

Остальные вызовы только читают: `docker info`, `compose config`, `compose ps`,
`compose logs`, `docker volume/network inspect`, списки ресурсов.

**Никогда** не удаляет тома и образы, не выполняет `prune`, не использует
`down -v`. `inspect` печатает команду `docker volume rm` как подсказку, но сам
её не выполняет.

Пишет три файла, все в корне проекта: `.env`, `.projectctl-state.json` и
временный файл на время атомарной записи. За пределы каталога проекта не пишет.

## Безопасность

- `SECRET_KEY`, `EMAIL_DELIVERY_QUOTA_SECRET` и `DB_PASSWORD` генерируются через `secrets.token_urlsafe(64)`,
  **никогда не печатаются** и не попадают в сообщения об ошибках.
- Проверяется представление всех значений, которые интерполирует Compose
  (`SECRET_KEY`, `EMAIL_DELIVERY_QUOTA_SECRET`, `DB_PASSWORD`, `EMAIL_HOST_PASSWORD`): `$`, кавычки, переводы
  строк и краевые пробелы отвергаются. Символ `$` Compose трактует как
  подстановку переменной и молча искажает значение.
- Существующий `.env` не перезаписывается; `init` может только один раз
  добавить отсутствующий `EMAIL_DELIVERY_QUOTA_SECRET`, скопировав текущий
  `SECRET_KEY` без вывода значения, чтобы сохранить активную часовую квоту.
  Смена ключа — только явным `init --rotate-secret`; quota-secret при этом не
  меняется. Запись атомарная (временный файл, `fsync`,
  `os.replace`), запись по символической ссылке запрещена, права `600`
  выставляются до подстановки файла.
- `--host` принимает только hostname или IP: без схемы, порта, пути, пробелов и
  управляющих символов. Попытка подставить переменную через перевод строки
  отклоняется.
- Наружу публикуется только `frontend`. `validate` разбирает
  `docker compose config`; неразбираемый JSON, отсутствие раздела `services`
  или ошибка Compose — провал проверки, а не «проблем нет».
- `APP_PORT` проверяется на занятость по IPv4, IPv6 и wildcard. Проверка
  рекомендательная: гонку между проверкой и стартом дополнительно разбирает `up`.
- `ALLOWED_HOSTS=*` запрещён в `production`.
- Все вызовы Compose получают `--env-file` с тем же файлом, который читает сам
  инструмент, поэтому интерполяция и окружение контейнеров берутся из одного
  источника.

На Windows права `600` не выставляются (там модель ACL). Ограничьте доступ
вручную:

```powershell
icacls .env /inheritance:r /grant:r "$env:USERNAME:(R,W)"
```

## Владение ресурсами

Перед `up` и `down` проверяется происхождение контейнеров, сетей и томов.
Смысл — не поднять стек на чужой базе и не остановить чужие контейнеры, если
имя проекта совпало.

Контейнеры несут метку рабочего каталога: если она отсутствует или указывает на
другой каталог, операция отменяется. Тома и сети такой метки не имеют вовсе,
поэтому владение подтверждается маркером `.projectctl-state.json` с
**отпечатками** ресурсов: `CreatedAt` и точка монтирования для тома, `Id` для
сети. Это отпечаток, а не настоящий Docker ID — у томов его нет; он ловит
пересоздание, но не подмену содержимого тома на месте.

Сверка идёт в обе стороны: замечается и появившийся неучтённый ресурс, и
исчезнувший записанный том — последнее означало бы, что следующий `up` молча
создаст пустую базу. Исчезновение сети нормально: её удаляет `down`.

Маркер пишется после успешного создания ресурсов в `up` либо явной командой
`adopt`. `validate` доверие не записывает никогда.

```bash
python3 scripts/projectctl.py adopt          # запросит слово ADOPT
python3 scripts/projectctl.py adopt --yes    # без запроса, для автоматизации
```

`adopt` сначала показывает, какие ресурсы будут признаны своими, и отказывается
работать, если контейнеры проекта созданы из другого каталога. Если ресурсов
нет, он сбрасывает маркер — это осознанный выход из ситуации, когда том был
удалён вручную.

## Типовые ошибки

| Сообщение | Причина и решение |
|---|---|
| `.env не найден` | Выполните `projectctl.py init` |
| `Docker daemon не отвечает` | Запустите Docker Desktop или `sudo systemctl start docker` |
| `Не найден файл конфигурации Compose` | Отсутствует `compose.yaml` или `compose.demo.yaml` |
| `Порт N занят другим процессом` | Освободите порт или смените `APP_PORT` в `.env` |
| `DEBUG=True` | Уберите из `.env` либо повторите с `--allow-debug` |
| `DEBUG=True в режиме production` | Отладку запускайте через `--mode demo` |
| `SECRET_KEY содержит '$'` | Compose исказит значение. Смените: `init --rotate-secret` |
| `ALLOWED_HOSTS=* недопустим в production` | Укажите домен явно |
| `PROJECTCTL_MODE=... не распознан` | Опечатка в `.env`: допустимо `demo` или `production` |
| `Сервис 'X' публикует порт наружу` | Уберите `ports` у backend/db/redis в `compose.yaml` |
| `вернул неразбираемый JSON` | Обновите Docker Compose до актуальной v2 |
| `занято контейнерами, принадлежность которых не доказана` | Имя проекта занято чужим стеком. Проверьте `projectctl.py inspect` |
| `Тома и сети уже существуют, но каталог не подтверждён` | Данные могли остаться от другого стека. Если они ваши — `projectctl.py adopt` |
| `Ресурсы изменились с момента присвоения` | Том или сеть пересозданы. Проверьте `inspect` и подтвердите заново |
| Регистрация возвращает `202` с предупреждением о доставке | Не заполнены `EMAIL_HOST_USER` / `EMAIL_HOST_PASSWORD`; заполните их и запросите код повторно |

## Тесты

```bash
python -m unittest discover -s scripts -p "test_*.py"
```

Юнит-тесты Docker не требуют. Integration-тесты поднимают Compose под отдельным
временным именем проекта и пропускаются, если Docker недоступен.

Полный цикл `up → health-check → down` идёт обычным путём, на временном имени
проекта, свободном порту и отдельном env-файле во временном каталоге — корневой
`.env` не читают ни инструмент, ни Compose. Включается отдельно, чтобы не
замедлять обычный прогон:

```bash
PROJECTCTL_INTEGRATION_UP=1 python -m unittest discover -s scripts -p "test_*.py"
```

В CI этот режим включён.

## Известные ограничения

- **TLS не проверяется.** `production` только выставляет флаги; сертификат,
  reverse proxy и реальная доступность HTTPS вне зоны инструмента.
- **Нет блокировки от параллельных запусков** — два одновременных `up` могут
  мешать друг другу.
- **Нет лимитов ресурсов**: `up --build` может заметно нагрузить хост.
- Отпечаток тома не защищает от подмены его содержимого на месте.
- Доступ к Docker daemon равносилен правам root на хосте: кто может запустить
  этот скрипт, тот может и напрямую управлять любыми контейнерами.
